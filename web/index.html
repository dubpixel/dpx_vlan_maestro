Overview

vlan_maestro.ps1 is a single-file, run-as-Administrator PowerShell wizard that provisions Hyper-V virtual switches and VLAN-tagged network adapters for live-event AV production facilities. It reads VLAN/IP topology from src/vlan_sets.json, falling back to hardcoded facility definitions if that file is missing or invalid.

No build step, no package manager — everything lives in src/. Launch it via src/vlan_maestro.bat (bypasses execution policy, pauses at the end) or run the script directly with PowerShell.

Requirements

  • Windows 10/11 Pro, Enterprise, or Education (Home edition doesn't support Hyper-V)
  • PowerShell 5.1+ (included with Windows)
  • At least one physical network adapter
  • Administrative privileges

Modes

1 · Normal
Full setup: pick a physical NIC, create a virtual switch, add a VLAN adapter per facility VLAN, assign IPs.
2 · IP only
Skip switch/adapter creation — just reassign IPs on adapters that already exist.
3 · Nuke all
Remove every non-default virtual switch and adapter. Gated behind a typed YES confirmation — destructive, verified on real Hyper-V hosts.
4 · Add single VLAN
Guided prompts for one ad-hoc VLAN adapter on an existing switch. Choose to apply to the live system, save to vlan_sets.json, or both.
5 · Manage facility schemas
Add a new facility or edit an existing one's VLANs/IP config — writes directly to vlan_sets.json. Never touches Hyper-V.
6 · Update existing
Diff a facility's VLAN list against an already-configured switch and add only what's missing. Drift is flagged, never auto-corrected.

Facilities

Facility VLAN sets are real venue network topologies, loaded dynamically from vlan_sets.json — the menu always reflects whatever's currently defined there.

Add or edit facilities interactively with mode 5, or by hand-editing src/vlan_sets.json directly.

vlan_sets.json schema

Each facility is a key under vlanSets:

{
  "vlanSets": {
    "4Wall": {
      "vlans": [
        {"Name": "196_Engineering", "VlanId": 196},
        {"Name": "218_Dante", "VlanId": 218}
      ],
      "ipBase": "10.{vlan}.{third}.{fourth}",
      "ipPrompts": ["third", "fourth"],
      "ipDefaults": {"third": 13},
      "subnet": "255.254.0.0"
    }
  }
}

Fields

FieldMeaning
vlansArray of {Name, VlanId} — Name becomes the virtual adapter name, VlanId must be 1–4094 and unique within the facility
ipBaseIP template. {vlan} is always auto-filled from the VLAN ID; other {tokens} are resolved via ipPrompts/ipDefaults
ipPromptsWhich {tokens} get asked for interactively at runtime
ipDefaultsFixed values for tokens not in ipPrompts
subnetDotted mask (255.255.255.0) or CIDR (/24)
Note: vlan_sets.json always wins over the in-script hardcoded fallback ($hardcoded4Wall etc.) whenever the file is present and valid. The fallback only activates if the file is missing or fails to parse.

Quick start

  1. Clone the repo: git clone https://github.com/dubpixel/dpx_vlan_maestro.git
  2. Run src/vlan_maestro.bat as Administrator (or powershell -ExecutionPolicy Bypass -File src/vlan_maestro.ps1)
  3. Pick a facility, then a mode, and follow the prompts

Full walkthroughs and example transcripts for every mode are in the README.

Testing

test/VlanConfig.Tests.ps1 (Pester) covers syntax checking, vlan_sets.json structure validation, and direct unit tests for every mode's core decision logic — VLAN ID range/collision checks, JSON read-modify-write correctness, and facility diffing. CI runs this suite plus PSScriptAnalyzer on every push via GitHub Actions.

What CI can't verify: hosted GitHub runners don't support nested virtualization, so CI can't exercise real Hyper-V cmdlets — only static/data checks. Real-hardware verification happens separately; check the CHANGELOG for which releases have been confirmed on a live host.
